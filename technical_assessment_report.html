1. Executive Summary & Objective

This report presents the complete deliverables for the AI-Driven Fullstack Developer Intern Technical Assessment. The objective is to replace error-prone warehouse spreadsheet logging with a robust, specification-driven Warehouse Receiving System (WRS).

Rather than relying on vague, one-shot natural language prompts, this application was engineered using a rigorous Specification-Driven Development (SDD) workflow. Every business rule was formally captured in a PRD, codified into a Technical Specification & Database Schema, executed via directed AI coding prompts, verified through 14 automated Vitest test scenarios, and containerized with Docker Compose.

Core Architectural Guarantee: Over-receiving is prevented at both the application API layer and enforced at the PostgreSQL database engine via row-level locking (SELECT ... FOR UPDATE) and SQL check constraints (chk_no_over_receiving). Document completion requires 100% item fulfillment.

2. Deliverable A: Product Requirements Document (PRD)

2.1 Business Problem & Proposed Solution

Inbound shipments currently logged via spreadsheets suffer from manual counting errors, lack of validation against vendor manifests, accidental over-receiving, and inaccurate stock balances. WRS introduces centralized inbound manifest tracking, dock receiving with instant ledger updates, and immutable audit logs.

2.2 User Roles & Responsibilities

User Role Responsibilities System Permissions
Warehouse Supervisor Inventory oversight, manifest planning, master catalog management, final delivery approval. Create product SKUs, register delivery manifests, mark documents as completed, view audit trail.
Warehouse Operator Dock unloading, physical goods counting, discrepancy verification, partial receipt intake. View manifests, record actual received quantities against line items, inspect available stock.

2.3 Key Business Assumptions & Decisions

  • Assumption A1 (Partial Receipts): Inbound deliveries frequently arrive across multiple pallets or split truckloads. The system explicitly supports partial increments (e.g. receiving 20 of 100 items today, and 80 tomorrow).
  • Assumption A2 (Strict Over-Receiving Rejection): Discrepancies exceeding the manifest expected quantity represent supplier errors. Total received quantity across all dock transactions cannot exceed the expected manifest count. Any excess attempt returns HTTP 422 Unprocessable Entity.
  • Assumption A3 (100% Completion Safeguard): A receiving document cannot transition to COMPLETED unless all registered line items are 100% fulfilled.
  • Assumption A4 (Dual-Entry Inventory Model): On-hand balance (inventory) is coupled with an append-only audit ledger (stock_transactions) to record every dock action, operator name, and timestamp.

3.2 Database Schema & Engine Integrity (PostgreSQL DDL)

-- Core Tables Summary
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sku VARCHAR(50) UNIQUE NOT NULL,
  name VARCHAR(255) NOT NULL,
  description TEXT,
  uom VARCHAR(20) NOT NULL DEFAULT 'PCS',
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE receiving_documents (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  document_number VARCHAR(50) UNIQUE NOT NULL,
  supplier_name VARCHAR(255) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
    CHECK (status IN ('DRAFT', 'PENDING', 'RECEIVING', 'COMPLETED', 'CANCELED')),
  expected_date DATE,
  notes TEXT,
  created_by UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE receiving_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id UUID NOT NULL REFERENCES receiving_documents(id) ON DELETE CASCADE,
  product_id UUID NOT NULL REFERENCES products(id),
  expected_quantity INTEGER NOT NULL CHECK (expected_quantity > 0),
  received_quantity INTEGER NOT NULL DEFAULT 0 CHECK (received_quantity >= 0),
  CONSTRAINT chk_no_over_receiving CHECK (received_quantity <= expected_quantity)
);

CREATE TABLE inventory (
  product_id UUID PRIMARY KEY REFERENCES products(id) ON DELETE CASCADE,
  quantity_on_hand INTEGER NOT NULL DEFAULT 0 CHECK (quantity_on_hand >= 0),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE stock_transactions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id UUID NOT NULL REFERENCES products(id),
  document_id UUID REFERENCES receiving_documents(id),
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  transaction_type VARCHAR(30) NOT NULL DEFAULT 'INBOUND_RECEIPT',
  notes TEXT,
  created_by UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

3.3 Concurrency Control & Row Locking Algorithm

To eliminate race conditions when two warehouse dock workers scan items simultaneously: 

// Atomic receiving algorithm inside ACID transaction:
await client.query('BEGIN');
const itemRes = await client.query(
  `SELECT * FROM receiving_items WHERE id = $1 AND document_id = $2 FOR UPDATE`,
  [itemId, documentId]
);
const currentItem = itemRes.rows[0];
const remainingExpected = currentItem.expected_quantity - currentItem.received_quantity;

if (incomingQty > remainingExpected) {
  await client.query('ROLLBACK');
  throw new BusinessError(422, 'Cannot receive more than remaining expected quantity');
}

// Increment received quantity, update inventory balance, and append to stock ledger:
await client.query(
  `UPDATE receiving_items SET received_quantity = received_quantity + $1 WHERE id = $2`,
  [incomingQty, itemId]
);
await client.query(
  `INSERT INTO inventory (product_id, quantity_on_hand, updated_at)
   VALUES ($1, $2, NOW())
   ON CONFLICT (product_id) DO UPDATE
   SET quantity_on_hand = inventory.quantity_on_hand + $2, updated_at = NOW()`,
  [currentItem.product_id, incomingQty]
);
await client.query(
  `INSERT INTO stock_transactions (product_id, document_id, quantity, created_by)
   VALUES ($1, $2, $3, $4)`,
  [currentItem.product_id, documentId, incomingQty, userId]
);
await client.query('COMMIT');
